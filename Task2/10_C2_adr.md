# ADR-001: Применение паттерна CQRS

## Контекст и предпосылки

В рамках развития платформы `NovaMarket` предстоит реализовать функционал интерфейса истории потребительских транзакций.

Необходимые для отображения данные распределены по нескольким изолированным доменным микросервисам:

| Данные | Ответственный микросервис |
| :--- | :--- |
| Заказ, позиции, жизненный цикл | `Order Service` |
| Платежные транзакции, реквизиты, чеки, возвраты | `Payment Service` |
| Логистика, временные интервалы (ETA), трек-номера | `Delivery Service` |
| Система оценок и отзывов | `Review Service` |
| Управление корзиной и повторными заказами | `Cart Service` |

Организация синхронной динамической агрегации данных «на лету» приведет к критической зависимости латентности интерфейса от производительности наименее эффективного компонента, повысит уязвимость к сетевым сбоям и негативно скажется на масштабируемости решения.

# Основное ешение

Для рассматриваемого сценария применяется архитектурный шаблон CQRS (Command Query Responsibility Segregation).

Развертывается специализированный микросервис `Order History Query Service`, оснащенный обособленным хранилищем данных для чтения (Read DB). Сервис функционирует на основе подписки на доменные события через шину сообщений:

| Событие | Изменения в read-модели |
| :--- |
| `OrderCreated` | Формирование записи истории с фиксацией неизменяемого снимка (immutable snapshot) состава, стоимости и адреса доставки. |
| `PaymentSucceeded`, `PaymentFailed`, `RefundSucceeded` | Актуализация платежного статуса, идентификатора платежа (`paymentId`) и признаков возврата. |
| `ReceiptIssued` | Регистрация идентификатора чека (`receiptId`) либо защищенного URI для скачивания. |
| `DeliveryCreated` | Включение параметров логистики, прогнозируемого времени (ETA) и трек-номера. |
| `ShipmentStatusChanged` | Обновление логистического статуса и финального состояния заказа. |
| `OrderPaid`, `OrderReadyForDelivery`, `OrderCancelled` | Синхронизация статусов заказа для списочного представления и детализации. |
| `ReviewCreated` | Маркировка позиций доставленного заказа как оцененных покупателем. |

Мобильное клиентское приложение взаимодействует с системой через шлюз `API Gateway`:
- `GET /me/order-history` — получение списка заказов;
- `GET /me/order-history/{orderId}` — получение детальной информации по заказу.

Исполнение мутирующих команд закреплено за профильными доменными сервисами:
- скачивание чека — `Payment Service`;
- публикация отзыва — `Review Service`;
- повторный заказ — `Cart Service` (с повторной валидацией текущих цен и доступности позиций).

Модель данных реализует принцип конечной согласованности (*eventual consistency*). Надежность доставки и обработки сообщений обеспечивается использованием паттернов `Outbox` на стороне издателей и `Inbox` с гарантиями идемпотентности на стороне потребителя.

## Альтернативные варианты

### 1. API Composition (Композиция через шлюз / BFF)
- **Суть:** Агрегация данных `API Gateway` или BFF-слоем в режиме реального времени путем синхронных вызовов к `Order Service`, `Payment Service`, `Delivery Service`, `Catalog Service` и `Review Service`.
- **Преимущества:** Минимальные затраты на проектирование на старте; гарантированное обращение к первоисточникам данных.
- **Недостатки:** Высокая зависимость производительности интерфейса от доступности всей цепочки сервисов; невозможность соблюдения целевых метрик $p_{98} \approx 0{,}3\text{ с}$ при сложной выборке строк заказа; усиление связанности шлюза с внутренней доменной моделью.

### 2. Event Sourcing
- **Суть:** Динамическая реконструкция текущего состояния заказа на основе непрерывного журнала событий (`Event Store`).
- **Преимущества:** Исчерпывающая прослеживаемость эволюции сущности; гибкость при пересчете проекций.
- **Недостатки:** Избыточная сложность для текущей стадии проекта; необходимость проектирования хранилища событий, схем версионирования и миграций; несоответствие целевой направленности микросервисной EDA-архитектуры.

### 3. Локальный CQRS в рамках Order Service
- **Суть:** Размещение read-модели непосредственно внутри структуры данных `Order Service`.
- **Преимущества:** Сокращение общего числа развертываемых сервисов; упрощение транзакционного контура.
- **Недостатки:** Нарушение границ доменной ответственности (`Order Service` вынужден оперировать бизнес-данными платежей и доставки); конкуренция write-нагрузки транзакций и read-нагрузки клиентских запросов; ограничение независимого горизонтального масштабирования.

## Дополнительна информация

### Положительные эффекты
- Обеспечение минимального времени отклика экрана истории за счет выполнения единого прямого запроса к оптимизированной read-модели.
- Сохранение строгой изоляции владения данными в write-сервисах.
- Возможность бесшовного подключения новых клиентских каналов к существующей read-модели без усложнения слоя композиции.
- Независимое масштабирование и тонкая настройка производительности сервиса истории под требования чтения.

### Риски и отрицательные последствия
- Увеличение сложности архитектурного ландшафта за счет внедрения дополнительного микросервиса и СУБД.
- Наличие кратковременной задержки синхронизации данных (*eventual consistency*).
- Необходимость администрирования версий событий и обработки сбойных очередей (DLQ, механизмы реплея).

### Зафиксированные ограничения
- История фиксирует статический снимок заказа на момент оформления, изолируя пользователя от последующих колебаний каталожных цен и наименований.
- Операция повторного заказа использует исходные идентификаторы товаров (`productId`) и объемы, однако итоговая стоимость и актуальное наличие проверяются заново.
- Бинарные файлы чеков не дублируются в хранилище read-модели: в ней содержатся исключительно ссылки или `receiptId`, а проверка прав доступа возложена на `Payment Service`.
